### Bugs found by the metrics and fixed

1. **A reload loop that never ended.** The fix for same-second edits back-dates a file's mtime, and that touch itself fired an fsevent. The Watcher reloaded again, about 10 empty compiles per second, forever.
   - Every save, and every `Server.fail`, queued behind those compiles. In 6s of idle after one save, P6 counted 59 reloads.
   - Fix: `Server.reload` drops paths whose content has not changed since their last compile, and returns `:noop` without running Mix. The check is on content, not mtime, because mtime has 1s resolution and a same-second edit must still compile.
   - Regression tests: a Watcher-level test (one save gives 1 compile; it was 25 before the fix) and a Server test.
2. **A rollback blamed on the wrong batch.** Mix deletes a module while it recompiles it. A guarded call in that window raises `UndefinedFunctionError`, and its `Server.fail` waits behind the compile. It then blamed the batch that had just loaded, and that rollback left a stale beam on disk.
   - Fix: the Guard records the failure time, and `Server.fail/4` blames only batches whose `loaded_at` (stamped after the load) is at or before it.
   - Regression tests: a failure stamped before a load cannot blame that batch, and a call that fails during a compile rolls nothing back.
3. **Re-runs blamed an innocent batch.** The re-run on rolled-back code was itself attributed, so a failure caused by corrupt state also rolled back an older batch that touched the same module. It is no longer attributed (Guard `attribute: false`). A test covers it.
4. **The first same-second edit after the reloader started was missed.** It had no recorded mtime. `Server.init` now seeds mtimes from `apps/*/lib`.

### Rulings (phase 2)

Each ruling gives the decision, and the cost if it is wrong.

1. **The whole reloader moved to `herdr_reload`, Server and Compiler included.** Guard has to call `Server.fail`, and reloading is VM-wide. Cost if wrong: modules to move back. herdr_reload's own modules stay reloadable.
2. **One `Guard.run_twice` instead of a wrapper per app.** Both apps depend on herdr_reload.
3. **`Compose` keeps the budget that was mandated.** It runs as one guarded call per frame. Frame cost at 15 panes is 659µs inline versus 734µs budgeted (+11%; it was 627µs before Guard). At 1 pane it is 84µs versus 108µs. Cost if wrong: about 75µs per frame per client.
4. **Re-run only after a rollback, and never blame the re-run.** Re-running an unattributed failure would double hang time and side effects. Cost if wrong: a second bad batch on the same path is not rolled back by that call.
5. **The table owner is a logic-free process, not `Native.Keeper` with an heir.** M1's module stays untouched. Cost if wrong: one owner process.
6. **Restore is keyed on the failure's own attribution, not a watermark.** It uses the oldest batch of the most recent rollback, and accepts a batch id at or below K. Each choice avoids losing actions, or restoring state that is already corrupt.
7. **The `state_at_load` provider is an app-env MFA reading the ETS mirror.** It never calls the Store, so it cannot deadlock.
8. **Only reload errors stay on screen.** Other errors expire after 8s. "view failed" is forwarded but not drawn. Identical notices skip the repaint, because the same text means the same screen.
9. **The control socket is a stopgap until M12.** It is local-only, and on macOS it is protected by the directory mode. It never blocks app start.
10. **Restarting the local client after a late crash is deferred to M7.** It would reopen the tty after `Tty.Owner` restored it, and a crash loop would keep toggling raw mode. Cost if wrong: the VM runs headless after a late client crash.
11. **Same-second edit detection.** Mtimes are seeded at init, and paths are skipped when their content is unchanged. Neither the paths in a batch nor the paths the watcher reports are realpath-normalised. Cost if wrong: on a project root behind a symlink, such as macOS `/var`, the back-date has no effect.
12. **Builds never run concurrently in this worktree.** Reviews may overlap. Cost: the work is serialised.

### Known gaps

- **Unbudgeted hangs.** A hang inside `Actions.apply` or the Store has no budget (ruled). The sessions' `Store.event` calls would time out after 5s.
- **Bad source recompiled.** A later batch can recompile a compile-time dependent of a rolled-back source from that still-bad source. These are Mix manifest semantics.
- **Re-save after rollback.** After a rollback, only a change to the source's content reloads it. Re-saving it unchanged, or touching it, does nothing.
- **Lost Store writes.** A `:kill` of the Store inside the 20ms debounce window loses the app writes made in that window (focus, mode, tab switch, split placement). A pane spawned in the window is still adopted into "scratch".
- **Client mirror leak.** A `{:client, pid}` mirror entry leaks when its session crashes and the client then exits without re-attaching.
- **Notice width.** Notice width counts characters, not cells. Fix it in the M16 width work.
- **store.ex size.** It is about 485 lines. Split the mirror and restore code out (M7).
- **Load-sensitive stall test.** `HerdrServer.Native.StallTest` failed once at load average about 21. No native code changed.

### Rulings

Each ruling gives the decision, why, and the cost if it is wrong.

1. **How Mix is driven in the VM.**
   - The compiler reenables `compile.all` and each `compile.<c>` from `Mix.Task.Compiler.compilers/1`. It runs them with `--return-errors --no-prune-code-paths` under `Mix.Shell.Quiet`, wrapped in `Mix.Project.in_project` when `project_dir` is given. It does not use `Mix.Task.rerun("compile")`.
   - Why: `rerun("compile")` returns `:noop` after the first run, because the subtasks stay marked. Under the `mix test` umbrella recursion, "compile" is routed to the root project. Pruning would strip the VM's other code paths.
   - Cost if wrong: `loadpaths` and protocol consolidation are skipped, so a dep added mid-session needs a VM restart.
   - Verified under `mix run` on the real umbrella: 3 apps found, HerdrScene edit compiled and diffed in 70ms.
2. **Mix is not hands-off in the VM.** `Mix.Compilers.Elixir.remove_and_purge/2` calls `:code.purge` and then `:code.delete` on every stale module. This was verified: a process running the generation before is killed on the second recompile, and on a compile error the stale modules are left deleted.
   - Consequence 1: before Mix runs, the Compiler soft-purges every cached module that has old code. If a holder is not on the allowlist, it aborts with `{:blocked, mod, holders}` and a `purge_blocked` notice, so no process is killed silently.
   - Consequence 2: after an error or a raise, the Compiler restores the modules Mix unloaded, from the cache.
   - Cost if wrong: one lingering old-code process blocks all reloads until it leaves the old code. Phase 2 should use fully-qualified loop calls or the allowlist.
3. **Same-second edits.** Mix's staleness check is "size changed, or mtime changed and digest changed", at second resolution, so a same-size edit in the same second is a `:noop`. The Server records each path's mtime at compile. When a path's mtime still equals that record, the Compiler back-dates the file by 1s.
   - Cost if wrong: an editor may warn "changed on disk" after a double save.
4. **How previous beams are captured.** The Server holds a cache `%{module => binary}` of what is loaded. It is seeded from disk at init, updated after every load and rollback, and taken from the cache at compile time. The cache is not read from disk, because Mix overwrites the beams.
   - Changed modules are found by stat (mtime, size, inode) before Mix runs, plus the bytes of beams written in the last 2s, then a byte-compare against the cache. A byte-identical rewrite is not fan-out.
   - Cost if wrong: a few ms per compile for the stat pass over all beams.
5. **After a rollback, disk keeps the bad beams.** Mix will not recompile them until the source changes. The stat diff keeps unrelated reloads from re-loading them.
   - Cost if wrong: restarting the VM loads the rolled-back code from disk.
6. **Guard: task or inline.** Guard runs inline (try in the caller) unless `budget_ms` is set. With a budget it starts a monitor-only worker plus a small watcher process that kills the worker if the caller dies. There are no links, so a caller that traps exits gets no stray messages, and an external kill of the worker becomes `{:exit, reason, []}`.
   - Why: a budgeted call costs ~4µs and copies its args into the worker heap (842µs for 1.6 MB). Inline costs 0.13µs. Phase 2 should budget only calls that can plausibly hang (`View.compute`) and run `App.Actions.apply` inline.
   - Cost if wrong: a hang in an inline call wedges that GenServer.
7. **The local-fun scan is costly on big results.** It is on in dev and test (349µs on a 1.6 MB result) and can be turned off per call with `scan: false`.
   - Phase 2 should scan `App.*` state results, not rendered cells.
   - Cost if wrong: dev keystroke latency on large state.
8. **Attribution when a module is in several batches.** Guard cuts the stack at the first Guard frame and adds `mod`. `Server.fail` then picks the newest live batch whose modules intersect the stack.
   - Rolling back batch k also rolls back every newer non-rolled-back batch that shares a module with the growing set.
   - That set is collapsed into one module-to-previous-beam map, with the oldest batch's beam winning, and each module is loaded once. Loading it twice would hit a blocked purge, because the guarded caller is still executing the intermediate code.
   - Cost if wrong: an unrelated newer batch that shares a module is rolled back too.
9. **Exercise window.** Each guarded success bumps `{mod, n}` and `{:total, n}` in ETS. A batch stays attributable while any of these holds:
   - its age is under `exercise_floor_ms` (default 5000);
   - fewer than `exercise_n` (default 20) guarded successes have happened since load;
   - one of its modules that is a guarded entry point has fewer than `exercise_n` calls since load.

   Helper modules that are never entry points count through the total. Both values are configurable as Server opts.
   - Cost if wrong: an edited entry point that is never called keeps its batch attributable until the batch is evicted (ring depth 8).
10. **Soft-purge allowlist policy.** The default is empty. Soft purge is retried, by default 3 attempts 10ms apart, and a hard purge happens only for modules on the allowlist.
    - Phase 2 fills it with pure modules that have no long-lived frames (`App.Actions`, `View`, `Layout`, ...).
    - Cost if wrong: a reload of a pure module is blocked by a transient caller.
11. **Compile runs in the Server process, not a Task.** The Server is a dedicated process, so app GenServers are never blocked. A guarded failure during a compile waits for it (call timeout `:infinity`), which the busy-server test checks.
    - Cost if wrong: during a compile, rollback latency is up to the compile time.
12. **`state_at_load` provider.** It is a `fun/0` or an MFA evaluated inside the reload call. It must not raise. It must not `GenServer.call` a process that may be blocked in `Guard -> Server.fail`, because that deadlocks; it should read an ETS mirror instead. This is recorded in the Server moduledoc and the plan's P2.
13. **What differs in a release.** Mix is absent, so `Reload.Compiler` and `Reload.Watcher` cannot run: `enabled` is dev-only. Guard, Ring, Loader and `Server.rollback`/`fail` do not need Mix, but the Server's init snapshot uses `Compiler.ebin_dirs` (Mix). A release would seed the cache from `:code.lib_dir/1` of the umbrella apps instead. Left for M18.
14. **`Loader.load` with a blocked purge returns `{:error, {:purge_blocked, holders}}`.** Forward-reload load errors are logged; a module whose current code Mix deleted autoloads the new beam from disk.
15. **The `LocalFuns` path is `[:a, 1, 1]` for `%{a: [1, {:x, fn}]}`.** The plan's `[:a, 0, 1]` was a typo against its own 0-based rule.

### Phase 2 recipe for M3's `safe_apply`

```elixir
case Reload.Guard.run(App.Actions, :apply, [state, ev], budget_ms: nil) do
  {:ok, new_state} -> new_state
  {:failed, _} ->
    # Guard has rolled back the attributed batch; re-run once on the old code.
    case Reload.Guard.run(App.Actions, :apply, [state, ev]) do
      {:ok, new_state} -> new_state
      {:failed, _} -> state  # phase 2: restore state_at_load + reconcile with Native.Keeper
    end
end
```

Signature:

```elixir
@spec run(module(), atom(), [term()], keyword()) :: {:ok, term()} | {:failed, failure()}
```

`failure` is one of:

- `{:raise, Exception.t(), stack}`
- `{:throw, term, stack}`
- `{:exit, term, stack}`
- `{:timeout, ms, stack}`
- `{:local_fun, module, path}`

Opts are `budget_ms` (nil runs inline), `server`, and `scan`.

- The Watcher has not run on Linux. Without `inotify-tools` it is disabled with a warning, and the CI image needs `inotify-tools` for the dev loop. That matters only if someone runs dev on Linux.
- A module that a rollback removes (it was new in the batch) keeps its beam on disk. A later call to it therefore autoloads the rolled-back code. Phase 2 should delete that beam on rollback, or leave it for Mix to replace.
- Deferred minors:
  - `Notices.subscribe` is not idempotent.
  - In the Loader, `retries` counts total attempts.
  - `pid_info.initial_call` mixes `{m, f, args}` and `{m, f, arity}`.
  - The watcher tests use fixed sleeps, and the stale-timer test does not reproduce the race with paths pending.
  - Restore after a compile error only covers modules that were loaded or whose beam is gone.
