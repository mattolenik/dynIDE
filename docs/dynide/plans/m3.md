# M3 server core and terminal client: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A multi-pane multiplexer in Elixir (splits, focus, keybinds, mouse,
status bar) whose server emits frontend-neutral scenes through the client
protocol, rendered by an in-VM terminal client, all running against an
in-memory fake kernel until M1/M2 land.

**Architecture:** `herdr_scene` holds the scene, event and protocol
contracts (pure data + validators + golden fixtures). `herdr_server` holds
pure `Layout`/`App.Actions`/`View` modules driven by thin GenServers
(`App.Store`, `Pane.Server`, `Client.Session`). `herdr_term` holds pure
`Input.Parse`/`Render.Compose` driven by thin GenServers (`Tty.Owner`,
`Client.Term.Input`, `Client.Term.Render`). Kernel calls go through
behaviours selected by config; `Kernel.Fake` implements them in memory. A
test-only `herdr_integration` app hosts cross-app tests and the bench.

**Tech Stack:** Elixir 1.20.4 / OTP 29 umbrella under `dynide/`, ExUnit, no new
Hex dependencies.

**Spec:** `docs/dynide/design.md` (binding: "Scene contract", "Client
protocol", "Supervision trees", "State layout", "NIF interfaces", "Rendering
pipeline", "Input pipeline") and the M3 section of
`docs/dynide/milestones.md`. Reference semantics (read-only Rust):
`src/layout.rs`, `src/ui/panes.rs` (`apply_pane_chrome`),
`src/config/model.rs` (default keybinds near line 1130), `src/raw_input.rs`.

## Contract decisions (rulings baked into the plan)

These are the decisions the tasks build on. Each is recorded in results/m3.md.

1. **Scene.Pane.rect is the content rect** (exactly the pane's terminal grid, rows map 1:1). Borders are `border: %{rect: outer_rect, edges: [:top | :bottom | :left | :right], title: binary | nil} | nil`. The focused pane is `scene.focus.pane`; the client chooses how to highlight it (no token on the border).
2. **`{:ref, pane_id, gen}` gen is the pane's layout generation** (bumped on resize or respawn), not the damage generation, so scenes are not re-pushed on every damage. Damage travels as `{:damage, pane_id, gen}` (ref transport) or `{:rows, pane_id, gen, rows}` (inline transport).
3. **Rows are read from a server-owned row cache, not from `Native.Vt.dirty_rows/1` by clients.** `dirty_rows` is consume-on-read per vt, so two clients would steal each other's damage. `Pane.Server` drains `dirty_rows` on damage into ETS table `:herdr_pane_rows` (one object per pane: `{pane_id, gen, rows_tuple}`, `rows_tuple` element n = packed row n). Ref-transport clients resolve rows with the MFA given in the attach ack (`{HerdrServer.Pane.Rows, :fetch, []}` → `fetch(pane_id) :: {gen, tuple} | nil`).
4. **Pane PTY size follows the latest active client** (tmux `window-size latest`): the client that last sent input or resize drives `Native.Vt.resize`/`Native.Pty.resize` for every pane of its rects. Other clients clip or blank-pad pane rows to their own rects.
5. **Client discovery is a registered name in the contract:** `HerdrScene.Protocol.endpoint/0` returns `:herdr_client_endpoint`, registered by `HerdrServer.Client.Endpoint`.
6. **Fast path:** `App.Store` publishes `:persistent_term.put(HerdrScene.Protocol.fast_path_key(), fast)` where `fast = %{gen: integer, pane: pane_id | nil, write: {M, F, A} | nil, intercept: MapSet.t({key, mods}), passthrough: boolean}` whenever focus, mode, modal state or keybinds change. `passthrough` is false in any mode other than `:terminal`. The client sends a key on the fast path iff `fast.passthrough and fast.write != nil and not MapSet.member?(fast.intercept, {key, mods})`, by `apply(m, f, [event | a])`; server side that is `HerdrServer.Pane.Input.key(event, pane_id)` (encode_key + pty write). After any event goes the slow path, the client holds all further events on the slow path until it receives `{:ack, seq}` for it, so a prefix key can never race the mode change it causes.
7. **Packed cells are M1's `HerdrScene.Cell`** (`dynide/apps/dynide_scene/lib/dynide_scene/cell.ex`, spec `docs/dynide/packed-cells.md`): 32-byte little-endian records, one per column, plus a per-row trailer for clusters over 12 bytes. Slicing/joining rows that may carry a trailer goes only through `HerdrScene.Cell.slice/3` and `concat/1` (never raw `binary_part`/`<>`). `Cell.slice/3` raises past the row end, so clipping/padding helpers live in `HerdrTerm.Cells` (built on `HerdrScene.Cell`). Chrome cells use link 0. Cursor, selection, dim and link hover are scene overlays, not cell attributes; the terminal client may rasterize an overlay as inverse/underline/faint cells in its own output. Nothing is added to `HerdrScene.Cell` (M1 owns it; needed changes are reported to the coordinator).
8. **Golden scene fixtures live in `dynide/apps/dynide_scene/priv/fixtures/scenes/<name>.exs`** as `inspect(scene, pretty: true, limit: :infinity, printable_limit: :infinity)` output, loaded by `HerdrScene.Fixture.load/1` (`Code.eval_file`). herdr_server's test regenerates them when `HERDR_UPDATE_FIXTURES=1` and otherwise asserts equality; herdr_scene's test validates every fixture.
9. **Property tests are hand-rolled** (`:rand` with a fixed seed, ≥ 1000 cases), no StreamData dependency.
10. **Architecture test strengthening:** herdr_term may not reference any `HerdrServer.*` atom (stronger than "App.* and server Native facades").
