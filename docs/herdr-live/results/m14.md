## Trust statement

A herdr-live plugin is ordinary code running as your user, with the same trust model as herdr's (plugins.mdx "Trust and security").

- **No sandbox and no review.** Install or link only what you trust. `plugin install` shows the commands it will run and requires `--yes`.
- **Process environment.** Plugin processes inherit the server VM's environment, as herdr's inherit herdr's, so your API keys reach them as they would in herdr. herdr-live adds only herdr's variables plus `HERDR_LIVE_BIN`/`HERDR_LIVE_API`.
- **Unset VM-internal variables.** For plugin commands and plugin panes, herdr-live unsets `HERDR_BROKER_SOCK` (the kernel handoff socket), `HERDR_LIVE_GEN`, `HERDR_LIVE_RUNTIME_DIR`, `HERDR_LIVE_LOG`, `HERDR_LIVE_HEADLESS`, `HERDR_LIVE_TEST_ON_SAVE`, `HERDR_LIVE_PERSIST`, `HERDR_LIVE_STATE_DIR` and `HERDR_LIVE_SESSION`. Panes get "" because a pty cannot unset a variable.
- **Ordinary shell panes** still inherit those variables, which predates M14.
- **Build commands** get no plugin or HERDR_* env.
- **API access.** A plugin can do anything the API can do, as in herdr (the whole CLI is the plugin API). The API's protection is M12's 0700 socket dir; M16's `client.token` sits in the same dir and is readable by any process running as you, plugins included. There is no per-plugin capability model, and herdr has none either.
- **Files.** Plugin roots are read-only by convention (managed checkouts). Config and state live in per-plugin dirs that herdr-live creates and never deletes. Plugin ids are escaped before they become path components. Symlinks out of a checkout are refused.
- **Lifecycle.** Commands still running when the server stops or hands off are not killed (herdr's behaviour). Plugins must stop their own background processes. Startup hooks run again in a VM that takes over by handoff (herdr's documented behaviour).

## Bugs found by the smoke and the reviews

- Pane objects did not carry the pane's name, so `pane list` never showed herdr's labels. `label` was added to the pane object (additive).
- Manifest parse errors were inspected Elixir terms. They are now the decoder's first line.
- A timeout leaked the port and the command's grandchildren. It now kills the process group and closes the port.
- A run did not end while a background descendant held stdout, keeping one of the 32 slots. Output now goes to files, and the run ends with the command, as in herdr.
- Plugin panes inherited `HERDR_BROKER_SOCK`. It is now blanked, and every consumer treats "" as unset.
- Relative `plugin link .` paths resolved against the server's cwd. The CLI now makes them absolute.
- A concurrent install of the same id could delete the winner's directory. Installs are now serialised per id.
- The Runtime ran its passes unguarded: a crash re-ran startup hooks and reset the in-flight count. The passes are now guarded, and startup runs once per VM.
- The event hub stayed subscribed after the last hook was removed. The Runtime now unsubscribes.
- `plugin install` with a real build hit the CLI's 60 s timeout. It is now `:infinity` with `--yes`.

## Rulings

Decisions made on the human's behalf, each with what it costs if wrong. Rulings 1-3 were accepted by the coordinator.

1. M14 publishes `Plugins.Keybind.mfa/1`, `pane.rename`, `pane split --no-focus` and spawn `cmd/args/env` in its early contract, and M17 builds on them. M17 drops its B7 and builds B3 on the spawn opts. Cost: none recorded.
2. `[[keys.command]] type = "plugin_action"` is parsed by a clause marked "M14 stopgap" in `HerdrServer.Config`, which M17's parser replaces on rebase. Other types get a diagnostic. Cost: two parsers for a while.
3. Plugin popups wait for M17's D4. `overlay` and `zoomed` open as a new tab. Cost: plugins that expect an overlay's restore-focus behaviour see a tab instead.
4. Install, link and uninstall are server API methods (herdr does them in its CLI), because the herdr-live CLI is a thin `erl -noinput` API client with no tty prompt. Cost: install needs a running server, and confirmation is preview plus `--yes`, not interactive.
5. M13 menus read a `:persistent_term` catalog that the Runtime refreshes (on change, and every 2 s), so plugin data stays out of `App.*`. Cost: a menu can be up to 2 s stale.
6. The link-handler hook is two additive edits in M9's files: `Pointer` puts the click mods into the `{:open}` target, and `PointerIo.open` consults `Plugins.Links.dispatch` first. Cost: an edit in M9's files the coordinator may have wanted routed.
7. The vendored copy of herdr-plugin-examples has no license file upstream. The README invites copying, the author is herdr's, and the copy is never pushed. Cost: it must be removed or licensed before any publish.
8. While a plugin method was published ahead of its task, its declared errors were only `not_available`, and the errors were narrowed per task. Cost: api.md churned across tasks.
9. `Manifest.first_line/1` has no non-binary fallback, because dialyzer proves Toml's reason is a binary shape. Cost: a crash if a toml bump changes the error type; a test would catch it.
10. Startup hooks run again on a handoff takeover, which is herdr's documented behaviour. Cost: a startup hook that builds layout duplicates it on each kernel-restart handoff.
11. The list of herdr events herdr-live does not emit yet is hard-coded in `Manifest`. Cost: a stale warning until M11 edits it.
12. Plugin pane `:plugin` meta is not persisted: a restored pane respawns `$SHELL`, so persisting the meta would mislabel it. Cost: after a restart, a former plugin pane is a shell that still has the plugin's title as its name.
13. Run output keeps the head of each stream, not the tail. Cost: a long build failure shows its start, not its end.

## Known gaps

- **Not ported:**
  - `plugin update`;
  - herdr's legacy config-dir seeding;
  - cleanup of old managed installations;
  - per-plugin checkout locks across VMs;
  - `pane.link.resolve`;
  - `stale_target`/`stale_content` checks on `pane.link.activate`.
- **CLI output** is the result object only, not herdr's `{"id","result"}` envelope. The examples match `"pane_id"` with a regex and work. A plugin that runs `jq '.result.pane.pane_id'` does not work yet.
- **Not emitted yet:** worktree events and `pane.agent_*`. `pane.exited`/`pane.moved` hooks never fire.
- **The keybind help modal** does not list plugin keybinds (M13's `custom` group is not built).
- **Commands have no default timeout**, so 32 hung commands block plugin runs until one exits (herdr is the same).
- **Deferred minors from the task reviews:**
  - `App.Commands.rename_pane` depends on `Modal.Menu.clear_name`;
  - a `whereis`/`send` race in the Store `{:plugin}` io clause drops a keybind silently if the Runtime dies in between;
  - the CLI leaves required-flag checks to the server;
  - ids are whitespace-trimmed;
  - the stderr/stdout file size on disk is bounded only by the timeout;
  - a pid-file window before the process-group kill;
  - `~/x` without HOME;
  - git clone inherits HERDR_* (harmless);
  - the preview omits other-platform builds;
  - a hard kill of the Runtime drops in-flight entries;
  - a failed startup is not retried;
  - a TOCTOU on `pane.open` and its notice drain;
  - `Regex.compile` on each click.
