### 2. Graceful `kernel-restart` during a typing loop loses no keystrokes

`bench/handoff/typing.exs`: one pane runs `sh -c 'stty raw -echo; exec cat > <file>'`. A
typer pipelines one ctl `{:write, id, <<c>>}` every 5 ms for 8 s (`a..z` cycled); at 3 s a
second connection runs `CTL_RESTART`. Afterwards the file is compared byte for byte with
what was sent.

After the rebase, at `0c7e000f` (load 17.29 -> 19.61):

```
TYPING sent=1600 written=1600 equal=true window_ms=12 max_reply_ms=26 in_window=281 errors=0 restart_ok=true restart_wall_ms=1417 kind=graceful
```

Before the rebase, at `c11c676a` (load 17.40 -> 16.85):

```
TYPING sent=1600 written=1600 equal=true window_ms=11 max_reply_ms=14 in_window=186 errors=0 restart_ok=true kind=graceful
```

Earlier at `e77955ac`: `window_ms=20 max_reply_ms=17 in_window=154`; before the fixes:
`window_ms=141 max_reply_ms=157 in_window=360`. Met: no loss, no reordering.

What happens to keystrokes sent during the window: the broker queues ctl requests from
`PREPARE` until `RESTORED` and then forwards them in order to the new VM, so they are
delayed by at most the window (here 11 ms; 186 of 1600 keystrokes had their reply
arrive inside it, the slowest 14 ms after sending). Bytes the old VM had accepted but
not yet written to the PTY are carried in the blob as `pending_input` and written by the
new VM right after `RESTORED`, before any queued request. For a real terminal client:
the old local client stops on `:begin`, keystrokes typed while no client reads stay in
the host tty's input queue, and the new VM's client reads them.

  An idle standby with no panes: 127600 KB.

  `Handoff.Link.init` until promotion, so `Native.Keeper` (and every Vt) starts only after

- Fallback when no standby is ready: still a handoff (fds and blobs come from the
  broker), only slower: a cold boot of about 0.6 s on a quiet machine, measured 1.0-1.1 s

- Snapshot cost (cargo, release, 10 000 lines of 79 chars, 10 MB max scrollback):
  `SNAPSHOT bytes=821632 encode_us=806 decode_us=1412`. The Snapshotter encodes only panes
  whose Vt gen, title, pwd or hidden flag changed, once per second, under the core lock

## Rulings

Each: decision, then cost if wrong. Plan rulings are in the plan; listed here as they
stand after execution.

1. Broker in Rust (`live/native/herdr_broker`); shell or escript cannot send SCM_RIGHTS. Cost: one more crate to build (the launcher builds it, about 0.1 s when fresh).
2. The VM spawns children (M1 `Pty.spawn` unchanged). After a restart the new VM is not their parent: orphans reparent to init/launchd, which reaps them; adopted panes detect exit with kqueue/pidfd and report `{:exit, id, :unknown}`. Cost: exit status is lost after the first restart (Known gaps).
3. `Keeper.open` sends `HOLD` with a CLOEXEC dup of the master synchronously before replying, so a `kill -9` after `open` returns cannot lose the pane. Cost: one DirtyIo send per open.
4. Terminal state crosses as ghostty's snapshot format, not ANSI replay: both screens, scrollback, modes, cursor, kitty keyboard stack, parser continuation (tracking enabled at 64 KiB). A blob that fails to decode adopts with an empty Vt. Cost: snapshot format compatibility across libghostty-vt upgrades is not guaranteed (empty screen after a vendor bump, children still alive).
5. Snapshot cadence 1000 ms for changed panes; `kill -9` restores the screen as of the last snapshot plus unread PTY output; output read by the dead VM after its last snapshot and input in its writer queue are lost. Graceful restart is exact. Cost: up to about 1 s of screen history on a crash.
6. Pane ids are preserved; `next_id = max(adopted) + 1`. Cost: none expected.
7. A VM learns its role over the link (`HELLO`, then `FRESH` or `ADOPT`*/`ADOPT_END`), with env `HERDR_BROKER_SOCK` and `HERDR_LIVE_GEN`; without the env var the VM starts as before (tests, iex). Cost: application start blocks in `Link.init` until promotion.
8. One warm standby VM, started only after a primary exists; `kernel-restart` replaces it with a fresh VM (the standby may carry an old NIF). Cost: about 130 MB RSS.
9. Graceful sequence: CTL_RESTART, stop standby, boot target, HELLO, PREPARE, freeze, final UPDATEs, PREPARED, ADOPT*, ADOPT_END(graceful), RESTORED, RELEASE (old VM releases its ptys without SIGHUP and exits 0). Any failure before RESTORED SIGKILLs the target, waits for it, then THAWs the old VM. Cost: no rollback after RESTORED.
10. Input during the window: ctl requests queue in the broker from PREPARE until RESTORED; in-VM writers see `{:error, :handoff}`/`:closed` from a frozen pane and must hold input. Cost: delayed input.
11. Crash-path redraw nudge (rows-1/rows resize) only for alt-screen panes that have not exited. Cost: a stale shell screen is not repainted.
12. Timeouts: target HELLO 120 s, PREPARED 5 s, RESTORED 5 s, old VM exit after RELEASE 5 s, standby stop 2 s, broker shutdown 15 s, frame send 5 s per `sendmsg`, `exit_grace` 5 s (below). Cost: a wedged step takes that long to fail.
13. Crash with no standby or failed adoption: boot a VM and adopt, 3 attempts, then the disk-restore hook stub (`handoff failed; disk restore not implemented (M8)`), a fresh VM, held fds closed. Cost: children die if all 3 fail.
14. SIGTERM/SIGINT/SIGHUP to the broker is a clean stop, never a handoff. VMs get `+Bi` (they share the broker's process group). Cost: none expected.
15. The broker holds opaque entries by key (`pane/<id>`, `app/store`) with 0..64 fds each; M2/M16 can hold tty fds and sockets under their own prefixes; entries the new VM has not claimed by RESTORED are dropped. Cost: none expected.
16. The broker absorbs `scripts/tty_guard.sh`'s job for `bin/herdr-live` (coordinator request after M2/M3): save termios at start, restore at exit, write tty_guard's exact restore sequence only when the last primary did not exit 0; skipped entirely when `HERDR_LIVE_HEADLESS=1`. `bin/live-demo` keeps the script. Cost: no restore between handoffs (the promoted VM's client re-initialises the tty).
17. M3 integration (M3 merged mid-milestone): the Store holds its app under `app/store` (coalesced to one HOLD per 100 ms, flushed on PREPARE) and a promoted Store adopts it instead of `close_all`; adoption is validated and run through `SafeApply` (`HerdrReload.Guard.run_twice/4` after the M4 phase 2 rebase), and a bad blob gives an empty app without closing any adopted pane. Cost: an empty layout (panes alive but unmapped) after a bad blob; a split followed by `kill -9` within 100 ms leaves an invisible pane.
18. Local terminal client hand-over: on PREPARE the server publishes the phase under `HerdrScene.Protocol.handoff_key/0` and waits up to 2 s for the process registered as `local_client_name/0` to exit (its `Tty.Owner` restores the tty) before freezing; the new VM's client starts once its endpoint exists; on `:aborted` herdr_term restarts its client. Cost: a brief repaint on graceful handoff; up to 2 s added if the client hangs.
19. Carried input is written by the new VM only after it sends RESTORED, and a clearing UPDATE (`pending_input: ""`) is staged before RESTORED; THAW sends a clearing UPDATE and writes the taken input back on the old VM. Cost: at-most-once with a microsecond window right after RESTORED.
20. ctl requests run FIFO in one monitored worker and only after `restored/0`; a crashing request still gets `{:error, {:crashed, reason}}`. Cost: one slow request delays the rest.
21. Freeze barrier: from `prepare` until `thaw`, `Keeper.open`/`close` return `{:error, :handoff}`; Link drains its ctl queue (bounded 2 s) before freezing; a write refused by a frozen pane is not acked. Cost: a pane open during the window fails visibly.
22. Primary link EOF: the broker waits up to `exit_grace` (5 s) for the exit status; exit 0 is a clean stop of herdr-live (detach/quit), anything else the crash path. Cost: a VM that exits 0 by accident ends the session; an external `kill -TERM` of the VM ends it too.
23. Preload every umbrella module at `Link.init` in broker mode and keep `binary_to_term(..., [:safe])`: a promoted standby must know every atom a blob carries. Cost: 133-494 ms of standby boot, more resident code.
24. Child identity: blobs carry the child's start time (`proc_pidinfo` / `/proc/<pid>/stat`); adoption re-reads it after registering the exit watch, and a mismatch or missing process adopts the pane as exited (never watched or signalled); EOF/EIO on an adopted master is an exit. Cost: platform code; a blob from an older VM without the key adopts unchecked.
25. Broker ignores HOLD/UPDATE/DROP from the old VM after PREPARED, and kills a VM whose HELLO pid differs from the spawned pid. Cost: none expected.
26. Raise `RLIMIT_NOFILE` to the hard limit (capped at 10240) at broker start. Cost: none expected.

Rulings 27-31 come from the rebase on M4 phase 2 (`e3ef3686`).

27. The carried app and M4's mirror coexist. `App.Store.init` checks the broker's `app/store` entry first, then the mirror. A new VM's ETS mirror is always empty, and the entry is claimed once. A carried adoption maps the live panes in `:herdr_pane_kernel` with `Rows.put_kernel_id/2` and starts their servers. It then writes the mirror at once, not after the 20 ms debounce, so a Store restart in that VM goes through M4's `Reconcile` path and never finds an empty mirror. In a VM that adopted panes (`Link.adopt_reason/0` not nil), `App.Restore.live/0` and `close_all/0` never close a keeper pane that nothing maps, because it may be an adopted child (a ctl pane, or a split just before the crash). `close_all` there only stops pane servers and forgets the map, as M5's `forget_all` did. Cost: an interrupted spawn in an adopted VM leaks its keeper pane (the child runs on, unmapped) until that VM exits.
28. Broker VMs defer the reload pipeline. `config/runtime.exs` sets `defer: true` when `HERDR_BROKER_SOCK` is set, and `HerdrServer.Application` calls `HerdrReload.Application.start_deferred/0` after `Link.restored/0`. Without this, M4's new `herdr_reload` app starts before `herdr_server`, so a standby (blocked in `Link.init`) would run a second watcher and Mix compiler on the same `_build`. Cost: reload starts a few ms after RESTORED. A promoted standby still runs the code it preloaded at boot, while its reload server seeds its beam cache from disk at promotion, so an edit saved between the standby's boot and its promotion is not loaded until that file changes again. Loading `:code.modified_modules/0` at promotion would fix this; it was tried, made the tty harness's `quit: log has herdr-live stopped` check fail every time, and was reverted. It is left for M6/M7.
29. The control socket moves with the primary. On PREPARE, after the freeze, the Link terminates the `HerdrServer.Control` child, which removes its socket, and THAW restarts it. Without this, the graceful target finds the old VM's live socket, runs without one, and the old VM then removes the socket as it exits. On a crash the promoted VM replaces the stale socket (M4 behaviour). Cost: `herdr-live rollback` answers "not running" from PREPARE until the new VM's supervisor is up, a few ms.
30. Controller ruling (reviewer finding): a fast-path write that returns `{:error, :closed}` holds the input only while `:persistent_term.get(Protocol.handoff_key(), nil) == :begin`. Otherwise it is an exited pane: the input is dropped and acked like any other write error, so an exited pane never wedges a session. The Link publishes `:begin` before it freezes any pane, so a frozen pane is always seen with `:begin`. Cost: none expected.
31. M4's guard replaces `SafeApply`. The Store's `adoption/1` and the session fast path now go through `HerdrReload.Guard.run_twice/4` with the Store's reload server, and the fast-path write runs with `scan: false`. The supervision order is Notice, Link, Keeper, Mirror, Snapshotter, then the app. Cost: none expected.

## Handoff contract for M3's Client.Session (implemented in this branch)

Server-side event, published by `HerdrServer.Handoff.Notice` (Registry pubsub,
`Notice.subscribe/0`) and forwarded verbatim by every `Client.Session` to its client as
the client-protocol message:

```elixir
{:handoff, %{phase: :begin | :aborted | :released | :adopted, gen: integer, panes: [pane_id]}}
```

- `:begin` (old VM, before it freezes panes): stop sending input. The Session holds input
  from here: it is not acked (one warning notice per handoff), so an at-least-once client
  keeps it. The local in-VM client stops (its tty restore completes before the server
  freezes anything; the server waits up to 2 s for it).
- `:aborted` (old VM, THAW): the restart failed; the Session replays held input through
  the normal path and resumes; the local client is restarted by herdr_term.
- `:released` (old VM): it is about to exit; sockets close. Re-attach to the endpoint of
  the new VM (same name in-VM; same socket path for remote clients, M16).
- `:adopted` (new VM, after RESTORED): panes are back with the same ids; attach normally.
- The current phase is also readable without subscribing at
  `:persistent_term.get(HerdrScene.Protocol.handoff_key(), nil)` (`:begin | :aborted |
  :released`, absent otherwise).

## Known gaps

- **Exit status of adopted children is `:unknown`** (accepted for M5). The new VM is
  not the parent, so it cannot `waitpid`. Remedy: make the broker, which outlives every
  VM, the spawner and reaper of pane children (or a Linux subreaper) and forward exit
  statuses (M8/M17).
- Linux not run for the final tree (see "Linux run").
- Cold handoff without a ready standby is 1.0-1.1 s under load, over the 1 s target.
- After the rebase, one `kill -9` run with `standby_ready=1` took 1085 ms (run 5 of the
  first bench). The cause was not found, and the next 12 runs had no outlier. M6
  should look at the broker log if it recurs.
- Kitty images are probably dropped by a snapshot restore (untested).
- A store-path key that races the freeze can still be acked and lost (marked `ponytail:`).
- A Store `close` refused during the freeze leaves that pane mapped in the next VM.
- Graceful failure after ADOPT: output the target already read is missing from the old
  VM's screen after THAW.
